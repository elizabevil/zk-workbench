# 通用代码与工程规则

本文件定义与具体产品功能无关的编码约束。项目已有 manifest、工具链文件、格式配置和代码模式优先；遇到缺失项不得编造既有约定。

## 1. 语言、语法与工具链版本

- **Rust 语法/edition**：以根 `Cargo.toml` 的 `edition` 为准；最低支持编译器版本由 `rust-version` 声明，工具链文件（如 `rust-toolchain.toml`）约束开发/CI 工具链。三者不得互相矛盾。新建项目尚未确定时先提议明确的 edition 和 MSRV，不得默认为最新稳定版或静默使用旧 edition。
- **TypeScript/JavaScript 语法**：应用代码使用 TypeScript；Vue SFC 使用 `<script setup lang="ts">`。TypeScript `target`、`lib`、模块解析策略以 `tsconfig` 为准，Node.js 版本以 `package.json` 的 `engines`/仓库版本文件及所选 Vite 版本兼容范围共同确定。不得依靠本机隐式默认值。
- **严格类型**：启用 TypeScript `strict`，Vue SFC 运行独立类型检查（候选 `vue-tsc`）。禁止以 `any`、`@ts-ignore`、无边界类型断言或关闭严格选项掩盖类型问题；确有外部边界不完整时，在最窄边界做校验和注释。
- **版本升级**：不在功能改动中顺手升级语言 edition、MSRV、Node、Tauri major 或框架 major。升级须单独说明兼容、迁移、平台影响和验证结果。
- **语法来源**：使用仓库锁定的编译器/解析器所支持的语法；避免依赖尚未进入项目工具链的实验特性、编译器 nightly 特性或浏览器/WebView 新 API。

## 2. 模块、包与依赖边界

- 先按职责组织模块；只有在存在独立职责、明确接口、可复用/独立测试/独立所有权等实际理由时才拆模块。不要仅因文件变长机械拆分，也不要把互相耦合的代码拆成大量转发层。
- Rust 默认使用私有模块和最窄可见性；`pub`、crate root 导出和跨 crate API 都是显式边界。新建 crate 仅用于有稳定依赖方向、独立测试/复用或构建隔离价值的边界，并更新 workspace、依赖图和文档。
- 前端按页面/功能域组织：页面负责组合，组件负责呈现和局部交互，composable/store 管理可复用状态，IPC/service 层封装 Tauri 调用。不得在组件中复制协议、权限规则或远端缓存一致性逻辑。
- 依赖方向从 UI/适配层指向领域服务和抽象；领域逻辑不得反向依赖视图组件。避免循环依赖、全局可变单例和仅为转发而存在的包。
- 优先复用现有依赖和标准库。新增依赖需说明必要性、维护状态、许可证、目标平台支持、体积/安全影响和替代方案；未经批准不得添加、替换或升级直接依赖。
- Rust 依赖版本和传递依赖由 `Cargo.toml` 与 `Cargo.lock` 管理；应用前端使用唯一选定的包管理器及其锁文件。锁文件纳入版本控制，CI 使用锁定/冻结模式安装。禁止多包管理器并行维护同一应用依赖图。

### 封装、抽象与拆分的判断

- 先写清需要保护的变化点、调用者和不变量，再决定是否引入封装。封装应隐藏易变实现、集中校验/资源生命周期，或让调用方不可能绕过关键规则；不能只为“看起来分层”增加一层转发。
- 当多个调用方共享同一业务规则，或一个外部边界需要统一校验、错误转换、重试/取消策略时，优先抽取明确接口；接口应表达业务能力，不暴露底层 crate、框架对象或无关配置细节。
- 单一调用方、单一实现、没有稳定变化点时，优先保留直接代码。不要基于“以后也许支持”建立 trait/interface、provider/manager/factory/adapter 层。
- 只有在有独立职责、依赖方向或独立发布/构建需求时拆 package/crate。文件或函数大不自动意味着新包；先考虑局部拆模块、提取纯函数或拆分职责。不得为了复用而制造循环依赖或跨层反向依赖。
- 抽象必须保留调用链可读性：避免多层 getter/setter、无语义 wrapper、仅转发参数的 facade、泛化配置对象，以及把简单分支包装成策略/插件系统。
- 不要让抽象吞掉错误、权限、取消或资源生命周期。关键失败必须可观测；抽象边界要有针对契约的测试，不能只测转发本身。

### 应避免的通用做法

- 避免“顺手重构”、大范围格式化、全仓重命名和与任务无关的依赖升级；让 diff 聚焦且易审查。
- 避免复制粘贴规则、魔法字符串/数字、含义不明的布尔参数和超大通用函数；优先命名类型/常量及能表达领域语义的小函数。
- 避免全局可变状态、隐式单例、隐藏 I/O 的看似纯函数、无边界缓存、无上限队列和无条件重试。
- 避免 `unwrap`/`expect` 用于可由用户输入、网络、文件或外部服务触发的失败；避免空 `catch`、忽略 `Result`、静默默认值和将错误伪装成空结果。
- 避免只通过类型断言/忽略诊断绕过边界校验；外部数据进入领域逻辑前必须解析并验证。
- 避免以快照或 mock 取代关键边界验证；测试应聚焦行为、失败语义和不变量，不为实现细节堆脆弱测试。

## 3. 接口、序列化与兼容性

- 进程内类型、Tauri IPC payload、持久化配置和日志事件属于不同边界；不得因为内部 Rust/TypeScript 类型相似就默认它们具有相同生命周期或兼容承诺。
- IPC 和持久化数据使用显式、可校验的 schema/类型；对缺失字段、未知枚举、非法长度、版本不匹配和旧数据迁移定义行为。避免向 UI 暴露内部 crate 错误或未经整理的调试对象。
- 序列化格式必须有明确编码、可空性、默认值、大小上限和兼容策略。敏感字段不得因派生序列化或调试输出自动暴露。新增/修改持久化字段要考虑旧版本读取与迁移。
- 序列化/反序列化不得悄悄丢弃未知数据或改变用户原始内容；转换须明确区分展示表示、编辑缓冲和实际写入数据。
- 公共 Rust API、Tauri commands/events、CLI 语法和磁盘格式变化须查找调用者、测试、文档与迁移路径。错误码/错误种类优先稳定，易变的人类可读文案不作为机器协议。

## 4. 错误、异步与资源

- 错误应保持可分类、可定位，并携带安全的操作上下文；只在适合的边界转成用户文案。不得静默吞错、用空值伪装失败或无限重试。
- 异步任务须考虑取消、超时、并发上限、背压、资源关闭和过期结果；定义连接/组件销毁时的生命周期。共享状态要明确所有权和同步策略。
- 不在锁持有期间执行不受控的网络/文件 I/O；避免阻塞 UI/异步 executor。大数据处理采用边界明确的分块/流式方案，先定义上限和失败行为。
- 文件、socket、子进程、Watcher、订阅、临时目录和密钥句柄需有确定释放路径；失败路径也必须清理。

## 5. 格式、检查和测试

- 格式化、lint、类型检查、单元/集成测试和打包是相互独立的质量步骤；一个步骤成功不能代替其他适用检查。
- 命令以仓库 scripts/CI 为准。初始化时确定 Rust formatter/linter、Vue lint/typecheck/test、构建命令，并保持本地与 CI 一致；规则必须可自动重复执行。
- 测试验证可观察行为与边界，不为凑覆盖率复制实现细节。错误、空值、权限拒绝、并发冲突、取消、过期数据、兼容迁移等关键分支按风险覆盖。
- 每项检查报告实际命令、环境、结果；没有运行则标明未运行。不得把计划中的验证写成已通过。

## 6. 构建、封装与发布产物

- **开发封装**：Cargo workspace/package 和前端 package manager 仅表达真实的模块/发布边界；避免重复依赖声明和无理由的多层包装。
- **Tauri 产物**：桌面安装包按平台构建；平台权限/capability、资源文件、图标、更新/签名配置遵守最小权限和平台规则。不能把开发服务器权限或调试配置带入正式包。
- **可复现构建**：使用锁文件和声明式工具链；构建依赖、资源输入、环境变量和版本信息可追踪。不得将本机绝对路径、个人密钥、凭据、真实集群地址或测试数据打入包。
- **资源与体积**：只封装运行必需的资源；大文件、编辑器语言包、平台二进制和可选功能按验证结果处理。新增打包资源须说明来源、许可证、目标平台和更新方式。
- **发布校验**：正式产物在目标操作系统/架构验证安装、启动、升级/卸载（若支持）、文件访问范围和签名。未做真实平台验证时，不得宣称该平台发布就绪。

## 7. AI 执行规则

仓库配置与锁文件是具体版本、语法选项和命令的权威来源；本文件是配置缺失时的约束，不是替代项目技术决策。发现规范与仓库冲突时先判断是否为有意迁移；不得静默改配置以消除冲突，应汇报并将不依赖该决策的工作先完成。

作出抽象/拆包决定时，在改动说明中简述：解决的具体变化点或不变量、为什么现有边界不足、抽象带来的成本，以及为何不采用更简单的局部方案。若没有明确收益，选择较简单的实现。
