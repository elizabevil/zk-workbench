# CHG-0002：ZK UI 产品需求逐步讨论

## 目的与流程

本文件是当前产品讨论的活动记录，承载推荐方案、负责人反馈、调查证据、待回答问题和决议。讨论中形成的推荐不自动成为产品基线；负责人选定方向后，才回写
`01-product/prd.md` 或相关设计/规格文档。

每个讨论主题依次记录：

1. 当前问题与已有基线。
2. 助手推荐方案、理由、风险及证据来源。
3. 负责人选择、修改或提出的新问题。
4. 收敛后的决定、影响文件和后续验证。

对话中的事实、选项、决定和待办均在本文件或其指定证据记录中持续落盘。若调查数据较多，另建有来源和日期的 `CHG-*`
调查记录并从此处链接，不在聊天中只留结论。

## 讨论主题 1：产品核心使用闭环

### 当前基线

PRD 已将产品定位为 ZooKeeper 桌面管理工作台，并列出连接工作区、节点浏览与编辑、状态一致性、巡检和审计等能力；但尚未明确首版用户最核心的端到端任务，以及哪些能力必须先完成才能称为可用产品。

### 推荐方案（待负责人选择）

首版主闭环建议定义为：

> 用户选择或新建连接 → 确认连接状态 → 定位并浏览目标节点 → 查看数据与 Stat → 安全地修改或执行管理操作 →
> 获得明确结果，并能在重连后判断数据是否仍新鲜。

首版优先保证这个闭环在单个工作区内可靠，再扩展为多集群并行工作、ACL 深度管理、四字命令巡检和本地审计时间线。连接配置与最近浏览位置可作为工作流连续性的必要部分；SSH
Tunnel、Watcher 实时推送等若尚未验证，不阻塞第一条可手动刷新的安全闭环。

### 推荐理由

- 闭环以用户目标组织功能，不以技术组件或 CRUD 清单组织产品。
- 能将连接、查询、读取、写入保护、结果反馈和状态新鲜度串成一条可验收路径。
- 先验证最关键的 Rust ZooKeeper 客户端能力和桌面交互，降低在非核心能力上投入后才发现读写链路不成立的风险。
- 多连接、巡检和审计有明确价值，但可以在主闭环成立后逐项加入，不必同时作为首版阻塞条件。

### 初始方向选项（已由后续决策收敛）

初始讨论曾提出以下首版主价值选项：

1. **可靠节点操作工作台（推荐）**：重点是连接、快速定位、查看、带版本保护的节点/ACL 操作和重连状态可信；巡检、审计增强随后迭代。
2. **集群运行巡检台**：重点是多集群连接、四字命令指标、阈值告警和运行状态判断；节点编辑作为辅助能力。
3. **节点数据维护与迁移工具**：重点是树/路径查询、数据编辑、格式化/diff、批量导入导出；实时 Watcher 和巡检可后置。
4. **其他方向**：请描述首版用户最重要的一项任务。

后续已确认以可靠节点操作为第一阶段目标，数据维护迁移和集群巡检分别排在第二、第三阶段。

### 证据与状态

- 类型：产品方向建议，基于当前项目草案做出的推论；不是外部事实，也不是已批准决定。
- 外部调查：本项暂不需要外部事实即可讨论。选定方向后，再针对对应高风险技术假设开展来源调查和验证。
- 状态：已由主题 5 的阶段优先级决议收敛。

### 决议

负责人已确认阶段优先级，见主题 5：首版聚焦单节点可靠操作，其次数据维护与迁移，再其次集群巡检。该决定已同步到产品需求和路线图。

## 讨论主题 2：多格式数据查看、编辑与高级命令入口

### 负责人已明确的方向

- ZooKeeper 中的数据可能是 JSON、YAML 等常见格式，应用需要支持格式美化等能力。
- 用户需要方便地查看和编辑节点数据。
- 常见操作由应用提供 UI 与快捷操作；底层或不常用功能保留命令行支持，CLI 是 UI 的一部分。

### 初步交互方案（待细化）

节点数据面板建议包含三个层次：

1. **原始数据**：展示实际读取到的字节内容，明确长度；无法按文本解码时提供十六进制/原始视图。
2. **格式视图**：可选择或识别 JSON、YAML、纯文本等格式，提供格式化、折叠、语法高亮和格式校验。自动识别只作为建议，允许手动切换。
3. **编辑与保存**：编辑器修改后显示未保存状态；保存前展示原值与待写入值的 diff，并使用 ZooKeeper version 检查并发修改。

关键安全语义：格式化和格式切换本身不修改 ZooKeeper 数据；只有用户明确保存后才写入。保存时必须明确最终写入字节如何由所选编辑格式编码。YAML
转 JSON 或 JSON 转 YAML 属于内容转换，不能作为无提示的显示格式化。

CLI 建议作为应用内的高级命令面板，而不是要求用户离开当前工作区：

- 命令默认绑定当前连接，并在提示区显示连接和目标路径。
- 高频、安全、可发现的操作优先提供专用 UI；低频或高级操作可用 CLI 调用。
- 写命令仍经过同一 Rust 核心的权限、版本保护、错误处理和本地审计，不提供绕过安全机制的“后门命令”。
- 输出可追溯到命令、连接、路径和结果；命令支持范围、危险操作确认、帮助和自动补全需要另行定案。

### 需要继续确认

1. 节点数据默认展示原始文本，还是按内容自动识别 JSON/YAML 并默认格式化？
2. YAML 编辑后是否原样以 YAML 文本写入 ZooKeeper，还是提供明确的转换/导出操作？（推荐保留用户选择的格式，不做隐式转换。）
3. 首版需要哪些格式：JSON、YAML、纯文本、XML、Properties、十六进制？
4. CLI 首版必须覆盖哪些操作？哪些仅需预留扩展能力？

### 状态

- 数据格式辅助与 UI+CLI 的组合方向：已确认。
- CLI 边界：已确认是面向 ZooKeeper 操作的应用命令行，不是系统 shell；细节见主题 3。
- 数据编辑交互和格式范围：待继续选择；初步方案仍不是完整规格。

## 讨论主题 3：应用命令行与工作台交互

### 负责人已确认

- 命令行面向 ZooKeeper 操作，是产品功能边界；不提供任意系统 shell。
- 命令行需要命令自动补全，体验目标可参考官方 zkCli 工具。
- 提供类似 shell 或 JavaScript 控制台的命令输入区域，支持保存命令。
- 支持一键执行保存的脚本文件中的完整流程，主要用于测试。
- 命令失败时应返回明确报错；脚本内每次查询都保存独立结果，结果默认折叠并允许用户展开查看。
- 脚本按顺序执行，第一条命令失败时立即停止后续执行。
- 换行符和分号 `;` 均作为命令结束符。
- 整体工作台交互参考 DataGrip 等多数据库客户端：多连接、对象树、数据查看/编辑和命令工作流可协同使用。

### 已同步的基线

- `01-product/prd.md`：新增 PRD-012 至 PRD-014，记录应用 CLI、脚本执行和多连接工作台。
- `03-specs/tree-query-connections.md`：记录 CLI 边界、补全能力、与 Rust 核心的复用要求，并列出脚本语义待决项。

### 助手推荐的首版脚本默认规则（部分待确认）

- 顺序执行；第一条命令失败立即停止（负责人已确认，不提供继续执行选项）。
- 执行前展示连接目标和写操作摘要；删除、批量写入等高影响命令需确认。
- 首版脚本保持为可读文本命令列表，不支持任意 JavaScript、系统 shell、循环或任意代码执行。
- 自动补全由命令语法和当前工作区上下文驱动；动态路径补全仅列出当前连接下权限可见的子节点。

### 负责人补充确认

- 第一条命令失败后立即停止，不执行后续命令。
- 换行符和分号 `;` 都是命令结束符。

### 负责人选择

- 脚本按文件顺序执行，并提供单行执行。
- 执行前展示目标连接和写操作摘要。
- 命令输入区域提供基础语法高亮。
- 可能需要简单的脚本目录管理与文本编辑器；该能力先列为待细化，不扩大为通用 IDE 或文件管理器。

## 下一批审批包：脚本编辑与工作区

以下是助手推荐方案，待负责人集中审批或修改：

负责人已回复“全部通过”，以下 A–D 作为已采纳的首版交互方向。

### A. 脚本文件与编辑器

- 使用 UTF-8 普通文本文件；每行一条命令，`;` 可在同一行分隔多条命令。
- 首版不支持变量、条件、循环、任意 JavaScript 或系统 shell。
- 提供应用默认脚本目录，也允许用户打开其他文本脚本；不做通用文件管理器。
- 编辑器提供文本编辑、行号、基础语法高亮、补全、执行当前行和执行全部。

### B. 执行结果

- 每次运行生成独立结果集；每条命令对应折叠结果项，显示行号、命令、状态、耗时和结果摘要。
- 首条失败命令立即停止；失败项突出显示错误，未执行命令标记为跳过。
- 结果暂时只在当前应用会话保留；跨重启保存后续再决定。

### C. 执行前摘要

- 显示目标连接名称/地址、命令数、写命令数，以及各写操作类型和目标路径。
- 执行前由用户确认该摘要；删除、ACL 修改和批量写入用醒目提示标出风险。

### D. 工作台布局

- 左侧连接/对象树；中间标签式主工作区；右侧 Stat/ACL 检查器；底部可折叠命令与脚本工具窗口。
- 数据编辑器和命令/脚本区可同时打开；每个工作区始终明确显示当前连接。
- 面板可调整宽度并记住本地布局；窄窗口允许折叠侧栏和检查器。

## 讨论主题 4：按路径选择 ZooKeeper 认证身份

### 问题与官方语义

ZooKeeper ACL 是逐个 znode 设置的，不会从父节点递归继承；客户端身份信息则与客户端连接/session
关联。一个进程可以维护多个独立客户端/session；同一连接也可能携带多个认证身份，但它们会共同参与该连接的 ACL
匹配。来源见 [Apache ZooKeeper 安全说明](https://zookeeper.apache.org/security/)、[Programmer’s Guide ACL 章节](https://zookeeper.apache.org/doc/r3.5.10/zookeeperProgrammers.html)
及 [官方 CLI `addauth` 文档](https://zookeeper.apache.org/doc/r3.9.6/zookeeperCLI.html)。

因此，节点路径绑定“账号/凭据”是 ZK UI 的本地工作区策略，不是 ZooKeeper 原生的每路径登录模型。不能只在一个共享 session
上按路径切换标签，却让之前添加的身份继续生效而不告知用户。

### 助手推荐方案（待负责人确认）

- 将凭据保存为本地“认证配置/身份配置”，实际秘密放在系统钥匙串或安全存储中。
- 允许用户把一个路径或路径前缀关联到一个默认认证配置；该关联仅保存在本地工作区，不写入 ZooKeeper ACL。
- 对不同认证配置使用独立 ZooKeeper client/session。用户切换到绑定路径时，应用选择对应连接身份；明确显示当前连接名和认证身份标签。
- 子路径默认可沿用最近匹配的父路径绑定作为 UI 选择规则，但每个 znode 的 ACL 并不继承，因此该默认只决定“用哪个身份尝试访问”，不代表该身份必有权限。
- 用户可以临时覆盖当前路径的身份；所有身份切换需可见，读写操作都显示实际使用的身份配置。
- 禁止在节点内容、脚本、路径标签或审计记录中保存密码/密钥；审计只记录认证配置名称或不可逆标识。

### 需要集中确认

1. 是否采用“本地认证配置 + 路径/前缀绑定 + 每认证配置独立 session”的模型？
2. 当路径绑定身份无法读取时，是否提示用户手动切换身份，还是允许按用户预先配置的候选身份依次尝试？（推荐不静默轮试，避免意外触发多身份访问和误判权限。）
3. 是否允许一个路径绑定多个候选身份？首版推荐只设一个默认身份并允许临时切换。
4. 子路径是否默认沿用最近匹配父路径的身份配置？

### 状态

- 用户提出“节点与验证信息绑定”及多节点身份验证需求：已记录。
- ZooKeeper ACL/session 语义：已查官方资料；设计结论属于基于该语义的产品建议。
- 本地路径绑定模型：待负责人确认。

## 讨论主题 5：产品阶段优先级

### 负责人已确认

1. 首版：单节点的可靠节点操作工作台。
2. 其次：节点数据维护与迁移工具。
3. 再其次：集群运行巡检台。

### 对需求基线的解释

- “单节点”按核心操作粒度理解为首版聚焦一个目标 znode 的可靠查看和操作；不自动解释为单用户或只允许一个集群连接。
- 节点数据维护与迁移属于第二阶段，不能反向扩大首版必须交付的功能；若其中某项是可靠节点操作闭环的必要条件，再单独说明。
- 四字命令巡检和集群运行指标属于第三优先级。
- 技术验证和平台验证按降低首版风险所需安排，不代表提升相应产品功能的优先级。
